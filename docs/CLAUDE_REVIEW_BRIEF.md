# Claude 项目复核简报

更新时间：2026-05-18

## 1. 复核目标

请从产品设计、数据结构、投研流程、前端交互、Prompt 可靠性和潜在 Bug 角度复核本项目。

本项目不是公开 SaaS，而是本地个人投研工具，后续可能部署到个人服务器自用。核心目标是批量分析加密项目 X 账号，辅助判断：

- 项目是否已经发币。
- 是否存在可信 CA。
- 是否存在候选 CA、钱包 / 金库地址。
- 是否有 TGE、空投、积分、测试网、白名单等机会线索。
- 项目质量、资本背书、风险和证据可信度是否值得继续人工跟踪。

## 2. 当前产品定位

### 2.1 已确认边界

- 只做本地个人工具。
- 暂不做公开 SaaS、多用户、团队协作。
- 不自动执行链上交易、申领、授权或资金操作。
- 不在证据不足时臆造 CA、TGE 时间、空投结论。
- 中文用户使用，前端和报告优先中文。

### 2.2 当前运行方式

- 本地 Web：`http://localhost:3000`
- 后端：Node.js HTTP server
- 数据库：SQLite，`data/app.db`
- 当前模式：真实 API，`MOCK_LLM=false`
- 数据源主线：Grok / xAI 的 X 搜索能力
- 汇总模型：GPT 或 Claude，可在前端切换

## 3. 核心流程

1. 用户在页面粘贴 X 账号列表。
2. 前端先根据项目总览表做输入查重。
3. 默认跳过已存在项目；需要更新旧数据时可选择重新分析全部。
4. 后端创建批次和项目记录。
5. Grok 按审计阶段搜索 X 证据。
6. GPT 或 Claude 归一化输出项目字段、排序、中文报告。
7. 前端展示批次结果、项目详情、跨批次项目总览。
8. 用户可导出 Markdown。

## 5. 关键设计更新

### 5.1 总览是项目主表，不是批次列表

项目总览用于长期沉淀项目库，不应重复显示同一 X 账号的历史记录。

当前规则：

- 按标准化 X handle 归并。
- 只展示最新有效记录。
- 旧记录显示为“已隐藏 N 条旧记录”。
- 失败批次默认不进入总览。
- 历史批次仍在“历史报告”中保留，作为审计记录。

### 5.2 输入前查重

用户粘贴账号后，前端根据项目总览中的 X handle 查重。

交互规则：

- 无重复：按钮显示“开始分析”。
- 有重复：展示重复账号列表。
- 默认按钮显示“跳过重复并分析”。
- 额外按钮“仍然重新分析全部”用于更新旧数据。

### 5.3 发币状态和 CA 状态拆分

原来“评分 / 等级 / 风险”容易和 CA 判断混在一起，现在拆成事实状态筛选。

发币状态筛选：

- 全部
- 已发币
- 未发币
- 发币线索
- 需复核

CA 状态筛选：

- 全部
- CA 已确认
- CA 待复核
- 无 CA

两组筛选可叠加，例如：

- 已发币 + CA 已确认
- 已发币 + CA 待复核
- 发币线索 + 无 CA
- 未发币 + 无 CA

### 5.4 CA 和钱包地址必须区分

当前要求模型输出：

- `ca`：确认 CA，只能来自高置信来源。
- `candidate_cas`：候选 CA，地址像合约但语境不够确定。
- `wallet_addresses`：钱包、金库、vault、team wallet、fee recipient 等非 CA 地址。

需要重点复核：是否存在钱包地址被误判为 CA，或 CA 被漏识别的情况。

### 5.5 评分体系准备重构

当前分数、等级、风险仍存在兜底启发式，不能完整代表项目质量。

已确认方向：

- CA 是事实字段，不参与“质量高低”打分。
- 后续评分应拆成：
  - 项目质量
  - 资本背书
  - 产品进展
  - 市场关注度
  - 风险
  - 证据可信度

## 6. 当前真实样本观察

已跑过多类 X 账号样本，包括但不限于：

- `@fair_vc`
- `@clashofperps`
- `@capacitr_xyz`
- `@aixbt_agent`
- `@pumpdotfun`
- `@polymarket`
- `@peptai_`
- `@AtlasOraFi`
- `@GenLayer`
- `@openservai`

已观察到的问题：

- 有的项目在 X bio 或帖子中已经公布 CA，但模型早期版本会漏识别。
- 有的地址是钱包 / 金库，不应当作为 CA。
- 有的项目已发币但 CA 存疑，应该进入“已发币 + CA 待复核”。
- 有的项目同一 X 账号多次分析，必须在总览去重。
- `@monad_xyz` 和 `@monad` 这类账号迁移目前不会自动合并，后续可能需要别名/迁移规则。

## 7. 已知风险与限制

- 当前主要依赖 X 搜索，缺少官网、docs、链上浏览器、CoinGecko / CMC 二次校验。
- 模型输出 JSON 虽有兜底，但仍可能因格式漂移导致字段缺失。
- 批次运行状态主要依赖当前 Node 进程，重启后只做有限恢复。
- 当前没有完整调用日志、成本统计、限流策略。
- 自动化测试不足，目前主要是 `npm run check`、`node --check` 和人工 smoke test。
- 项目无鉴权，不适合直接暴露公网。

## 8. 希望 Claude 重点复核的问题

### 8.1 产品设计

1. 总览作为“唯一项目主表”的设计是否合理？
2. 历史批次作为审计记录保留，是否还需要更明确的版本对比？
3. 输入查重默认跳过重复项目，是否会影响用户想更新旧数据的体验？
4. 发币状态和 CA 状态拆分后，筛选维度是否足够？
5. 是否还需要增加“仅看有空投线索 / 仅看 TGE 观察 / 仅看高风险”？

### 8.2 数据模型

1. `ca`、`candidate_cas`、`wallet_addresses` 三分类是否足够？
2. 是否需要增加 `ca_confidence`、`ca_source_type`、`ca_verified_at`？
3. 是否需要给项目建立稳定 `project_id`，避免 handle 迁移导致重复？
4. 是否需要独立维护别名表，例如 `@monad_xyz -> @monad`？

### 8.3 Prompt 和模型输出

1. Grok prompt 是否足够强调 X bio、置顶帖、近期帖、CA 语境？
2. GPT / Claude 汇总 prompt 是否足够避免把钱包地址误判为 CA？
3. 是否应该要求模型输出证据 URL、证据摘录、证据时间？
4. 三阶段审计的 Fast / Deep / Verify 是否应该有更明确的差异？

### 8.4 代码与潜在 Bug

1. `src/db.js` 的总览去重逻辑是否会误隐藏重要记录？
2. `public/app.js` 的发币 / CA 分类规则是否过度依赖中文字符串？
3. 前端筛选状态是否需要持久化到 URL 或 localStorage？
4. 失败批次默认不进入总览是否合理？是否应保留“失败/需复核”筛选入口？
5. 当前无前端构建工具，纯静态 JS 是否还适合继续迭代？

## 9. 代码入口

核心文件：

- `src/server.js`：HTTP API 与静态资源服务。
- `src/analyzer.js`：批次调度、Grok 调用、GPT / Claude 汇总。
- `src/models.js`：Grok prompt、汇总 prompt、模型 API 客户端。
- `src/db.js`：SQLite schema、项目总览去重、统计。
- `src/markdown.js`：Markdown 报告生成。
- `public/app.js`：前端交互、筛选、查重、表格、详情。
- `public/styles.css`：页面样式。
- `public/index.html`：页面结构。

文档：

- `docs/PROJECT_DESIGN.md`：完整设计文档。
- `docs/PROJECT_STATUS.md`：当前进度。
- `docs/PROJECT_REANALYSIS_2026-05-18.md`：真实样本复盘。

## 10. 建议复核输出格式

请按以下格式输出：

1. 总体判断：项目方向是否合理，当前实现是否支撑个人投研使用。
2. P0 问题：会影响正确性、CA 判断、数据可信度或核心体验的问题。
3. P1 问题：会影响效率、可维护性、报告质量的问题。
4. P2 建议：后续增强项。
5. 对 Prompt 的具体修改建议。
6. 对数据结构的具体修改建议。
7. 对前端交互的具体修改建议。
